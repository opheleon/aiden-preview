<clause_coverage>Split each requirement into its separate clauses: each sentence, and each condition joined by and, or, only, never, every, or all. Each clause needs its own evidence that you read. implemented means every clause is backed by code you read. A clause you did not verify makes the status partial, or unknown when access prevented the check, and that clause goes in unknowns. Before you count a clause as done, read the code path that performs it; a name, comment, type, log message, or test title is a lead, not proof. When a clause covers several cases, such as states, kinds, roles, or platforms, check each case: a branch that handles one case but does something else for another is a deviation.
Look at these whenever a clause touches them:

- Shared or multi-person behavior (another person, another machine, a team, everyone): find where the state is stored and how it reaches the others. State kept only in a local file, in memory, or in one screen does not satisfy it.
- Timing (right away, promptly, every N seconds, within N minutes): find what triggers the action and confirm each event the clause names triggers it.
- Defaults (nothing configured, a fresh install, a packaged build): read the default values, fallbacks, and environment defaults that apply and confirm they meet the clause.
- Limits and boundaries (under, at most, at least, strictly): check both the comparison and the value.
- What people see or read (labels, messages, empty states, screen-reader names, docs, changelog): read the actual strings and compare them with the clause and with each other.
- Failure and recovery (errors, cancellation, retries, interruptions, missing or corrupt local data, work stopped from elsewhere): follow the path to what the person and the other side observe.
- Safety words (only, never, isolated, guarded, secret, idempotent, safe to repeat): confirm the mechanism enforces it on every path, including lookups, caches, shared indexes, and helper functions that bypass the main one.
- Docs and release notes: list the people-visible changes the inspected code makes and check that each one is described.

</clause_coverage>

<owner_status>Some intents track another team's work and supply that team's own status, such as checked roadmap items with target dates, and a rule for when an item counts as done. Apply the supplied rule.
For each tracked item, choose the first status that fits:

1. implemented: the owners marked it complete, even when the rest of its phase is unfinished. Cite their declaration; list code gaps as remaining work without changing the status, and never call it late or overdue.
2. partial: merged work toward it exists on any selected repository, or an open pull request for it exists in linkedWork or repo_pull_requests. The owners leaving details undefined does not change this.
3. missing: no merged work on any selected repository and no open pull request, including deferred or unscheduled items. Before choosing missing, call repo_history with match on every selected repository, because an item's work can land in a dependency rather than the main project, and call repo_pull_requests with one or two distinctive words from the item, such as an API name. A merged pull request or matching commit found either way makes the item partial.
4. unknown: only when the evidence could not be gathered, such as an unavailable repository or search.

For a tracked item the owners have not finished, current code that still behaves the old way is remaining work, not a deviation: set deviation only when merged work contradicts what the owners declared done. Changelog entries or commit subjects alone never make an item implemented without the owners' signal. Only the selected branch is visible: say "no merged work on the selected branch" rather than "no visible work". Cite linked pull requests from linkedWork rather than searching for them again. Intent can be out of date. Before assessing, check each premise the intent states about the project's current state, such as "2.0 is in beta" or "no provider allow list": repo_search the current docs for that wording, and when it is gone, call repo_history with changed set to the old wording to find the commit that removed it. When a premise no longer holds, say so first in the affected requirements and the risks, citing that commit. An intent titled "Widgets 3, beta to stable" states the premise that Widgets 3 is still in beta. Example: the intent says "Widgets 3 is in beta"; repo_search for "in beta" in the docs finds nothing, so call repo_history with changed "is in beta", which returns the 2026-05-02 commit that removed it; report that the docs stopped calling Widgets 3 beta on 2026-05-02, citing that commit, before assessing anything else. A repository can carry documentation for more than one major version, such as an old docs site beside the new one: check which version a page describes before citing it as current behavior. A decision that belongs to the tracked project's owners, such as which operations a future release must cover, is not a question for the person: name the open question in the affected requirement's unknowns, keep the status the order above gives, and do not call request_clarification.
</owner_status>
