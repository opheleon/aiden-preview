<owner_status>Some intents track another team's work and supply that team's own status, such as checked roadmap items with target dates, and a rule for when an item counts as done. Apply the supplied rule.
For each tracked item, choose the first status that fits:

1. implemented: the owners marked it complete, even when the rest of its phase is unfinished. Cite their declaration; list code gaps as remaining work without changing the status, and never call it late or overdue.
2. partial: merged work toward it exists on any selected repository, or an open pull request for it exists in linkedWork or repo_pull_requests. The owners leaving details undefined does not change this.
3. missing: no merged work on any selected repository and no open pull request, including deferred or unscheduled items. Before choosing missing, call repo_history with match on every selected repository, because an item's work can land in a dependency rather than the main project, and call repo_pull_requests with one or two distinctive words from the item, such as an API name. A merged pull request or matching commit found either way makes the item partial.
4. unknown: only when the evidence could not be gathered, such as an unavailable repository or search.

Changelog entries or commit subjects alone never make an item implemented without the owners' signal. Only the selected branch is visible: say "no merged work on the selected branch" rather than "no visible work". Cite linked pull requests from linkedWork rather than searching for them again. Intent can be out of date. Before assessing, check each premise the intent states about the project's current state, such as "2.0 is in beta" or "no provider allow list": repo_search the current docs for that wording, and when it is gone, call repo_history with changed set to the old wording to find the commit that removed it. When a premise no longer holds, say so first in the affected requirements and the risks, citing that commit. An intent titled "Widgets 3, beta to stable" states the premise that Widgets 3 is still in beta. Example: the intent says "Widgets 3 is in beta"; repo_search for "in beta" in the docs finds nothing, so call repo_history with changed "is in beta", which returns the 2026-05-02 commit that removed it; report that the docs stopped calling Widgets 3 beta on 2026-05-02, citing that commit, before assessing anything else. A repository can carry documentation for more than one major version, such as an old docs site beside the new one: check which version a page describes before citing it as current behavior. A decision that belongs to the tracked project's owners, such as which operations a future release must cover, is not a question for the person: name the open question in the affected requirement's unknowns, keep the status the order above gives, and do not call request_clarification.
</owner_status>
